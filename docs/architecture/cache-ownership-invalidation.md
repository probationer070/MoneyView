# Cache Ownership And Invalidation

This note documents the current cache owners, query keys, invalidation triggers, and stale-read rules for the high-change MoneyView workflows covered by Track O4.

## Rules

- SQLite tables are the source of truth for mutable app state such as watchlist rows, corporate company rows, corporate metric overrides, comparison snapshots, OHLCV bars, and news articles.
- React Query caches are frontend transport caches. They may prevent redundant refetches, but they do not define canonical freshness.
- Browser `sessionStorage` caches are continuity caches. They may restore the last successful heavy payload after reload, but the UI must treat mismatched snapshots as stale instead of silently reusing them as current.
- Ticker-scoped `sessionStorage` caches must not render as current data for a different active ticker. If the cached snapshot ticker does not match the active ticker, the owning component should suppress the cached payload and show the idle/refresh state instead.
- Request-scoped `sessionStorage` caches for portfolio analysis may render only when the cached snapshot still matches the active universe, benchmark, custom ticker list, holdings signature, ticker list, weights, and date filters. Mismatched snapshots are review signals, not display data.
- Backend in-memory TTL caches are process-local optimizations. They must be keyed by the source inputs that affect the result and can disappear on process restart.
- Durable read models must name their write model, projection path, invalidation trigger, stale tolerance, and user-visible freshness metadata before new storage is added.

## Local-First Cache Defaults

- React Query defaults live in `apps/web/components/providers/AppProvider.tsx`: 1 minute `staleTime`, 5 minute `gcTime`, reconnect refetch enabled, and window-focus refetch enabled unless a query opts out. Heavy explicit-refresh queries keep refresh tokens in their key or `enabled` gate so these defaults do not trigger background heavy recomputation.
- Backend statement cache defaults to 48 tickers for 5 minutes. This holds the normal local watchlist plus ad-hoc corporate searches without keeping unbounded Yahoo DataFrame bundles resident.
- Backend OHLCV provider fetch cache defaults to 96 ticker/period/table entries for 30 seconds. This is intentionally short because SQLite is the durable cache and provider fetch coalescing only needs to cover adjacent endpoint calls.
- Backend portfolio attribution cache defaults to 128 request variants for 3 minutes. The report cache defaults to 64 payloads for 3 minutes. These cover repeated local refresh/export actions while bounding memory when users vary dates, benchmarks, and weights.
- Browser `sessionStorage` caches keep only one last-successful payload per heavy panel key. They are not collection caches and are snapshot-guarded before rendering.
- Increase max sizes only for measured workflows with larger local universes; prefer shortening TTLs or adding projection storage before treating in-process caches as durable read models.

## Mutation Guidance

### Watchlist And Portfolio Mutations

- Watchlist upsert/delete/sync/resync commands refresh `["portfolio-watchlist"]`, `["portfolio-watchlist-sync-status"]`, `["portfolio-browser-companies"]`, `["corporate-companies"]`, and `["corporate-watchlist-holdings"]`.
- Allocation-only autosaves patch `["portfolio-watchlist"]` and skip company invalidation because company registry data does not change.
- Attribution and comparison analysis caches should not refetch on every watchlist mutation. Snapshot mismatch and manual analysis refresh make stale state reviewable and avoid redundant heavy requests.
- Portfolio session-cache restores are guarded by snapshot equality. If holdings, weights, benchmark, universe, custom ticker input, or attribution dates differ, the cached comparison/history/attribution payload is withheld until a matching query result or explicit refresh exists.

### Corporate Company And Metric Mutations

- Corporate company add writes the company registry and updates or invalidates `["corporate-companies"]`; Portfolio company search also consumes `["portfolio-browser-companies"]` and must be invalidated when the same registry changes from Portfolio.
- Metric override writes affect same-ticker metric hydration, audit, DCF inputs, and future comparison snapshots. If metric persistence becomes a React Query mutation, invalidate the affected ticker's `corporate-metric-audit`, `corporate-metric-history`, `corporate-quarterly-statements`, and any active live comparison key rather than broad-refetching all corporate queries.
- Existing comparison snapshots are historical read models. Metric edits should create future snapshot versions; they should not mutate old snapshot rows.
- Corporate DCF session-cache restores are ticker guarded. A cached DCF result for `AAPL` must not populate the Backend DCF card when the restored or selected active ticker is `MSFT`; the card should stay in its refresh-to-calculate state.

### Source Data And Provider Refreshes

- Yahoo statement cache invalidation is currently TTL-based. A future explicit provider refresh should evict only the affected ticker from `_YAHOO_STATEMENT_CACHE`.
- OHLCV provider fetch cache invalidation is ticker/period/table scoped. A future explicit price-history refresh should evict only the affected `_provider_fetch_cache` key and update SQLite rows.
- Formula-version changes should be represented by new calculation-version metadata and, for durable projections, new projection versions rather than in-place rewrites.

## Review Checklist

Before adding or changing cache-backed behavior, document these points in the owning PR or architecture note:

- source write model
- cache or projection owner
- key shape, including ticker, period, benchmark, assumption set, formula version, and request snapshot where relevant
- TTL or stale-read tolerance
- invalidation trigger and scope
- user-visible stale/fallback metadata
- targeted verification command
