Macro Signals Tab

Tab identity
- Sidebar label: Macro Signals
- Route: /signals

Purpose
- Show this week's FRED-based macro rule verdicts and the heuristic scenario probabilities they
  feed: A (upside), B (correction), C (not yet named; the page shows "A/B/C" until the owner
  names it).
- Let the owner enter the three manual signals for the week, and re-run the engine on demand.

Design intent
- The probabilities are a heuristic, not a model estimate. The disclaimer is shown on every
  render, verbatim, in the page footer (data-testid="disclaimer"):
  "These probabilities are a heuristic built from subjective likelihood ratios, not a statistical
  model estimate, and are not investment advice."
- A data problem is content, not an error. A stale rule stays on the table, dimmed, with its
  reason shown under the signal name (the API's `note`). A FRED failure never blanks the page.
- A failed run or a failed manual save is an alert (role="alert"). The run's own failure list
  (FRED errors that fell back to cache or to stale) is shown in a status region, but only for the
  run just made; it is not kept across a reload.
- Korean labels are not shown yet. The page strings sit in app/signals/copy.ts in English;
  `label_ko` is already returned by the API for the design-system plan's i18n task.

Layout structure
- Header: title "Macro Signals" and the subtitle.
- Summary bar: the week's most likely scenario, the three probabilities, last run time, and the
  "Run now" button.
- Run failure alert and, when present, the list of data problems from the last run.
- Signal table: one row per rule with direction (A/B), state, value, threshold, observed date and
  the rule's contribution in percentage points to A, B and C. Stale rows are dimmed and carry
  their reason.
- Probability trend chart: the last 26 weeks of A/B/C. A dashed line marks a week whose
  rules_version differs from the previous week ("rules changed").
- Manual input panel: the three manual rules for this ISO week (KST), each with a state
  (triggered / near / not triggered), an optional note, and Save. An unset rule reads "Not set this
  week" and is left out of the probability.
- Footer: the disclaimer above.

Key sections
- Summary bar: GET /api/v1/signals/latest; POST /api/v1/signals/run for "Run now".
- Signal table: the `results` of the latest snapshot, in rules.yaml order.
- Trend chart: GET /api/v1/signals/history?weeks=26.
- Manual panel: rules from GET /api/v1/signals/rules (kind "manual"); saves with
  PUT /api/v1/signals/manual/{rule_id}, which rescores the current week without touching FRED.

Important behavior
- Rules, thresholds, likelihood ratios, the prior (A 0.35, B 0.45, C 0.20), the bounds [0.05, 0.85]
  and the weights live only in apps/api/services/signals/rules.yaml. Each week is recomputed from
  the prior; last week's result is never multiplied in.
- Manual inputs accept only triggered, near and not_triggered. "Data stale" is never a manual value.
- A week with no manual input leaves that manual rule out of the results and the probability. It is
  not counted as not_triggered.
- Bounded probabilities are computed by bounded_normalize (C1): values pinned at the bound, the rest
  renormalised, repeated until every value is in bounds.
- The page's copy is English only for now (C11).

Corrections from the implementation plan (spec appendix, "구현 계획에서 확정한 수정 사항 (2026-10-12)")
- C1  Probabilities are bounded, not clipped and renormalised: pinned values never leave [5%, 85%].
- C2  Staleness is per rule: daily 7 days, Brent 14, monthly 80.
- C3  b_fed_hike compares the latest value with the value `lookback_days: 7` before as_of, not with
      the previous snapshot, so the rule stays pure.
- C4  Two integration tests: with 3 manual inputs, 11 results; with none, 8 results.
- C5  Percent changes and means are rounded to 9 places before comparison, so 0.250 triggers.
- C6  Endpoints are under /api/v1/signals/*.
- C7  No APScheduler: an asyncio loop checks hourly (see the schedule below).
- C8  FRED is read through FREDCollector.fetch_observations(), which raises, uses a 15 s timeout and
      redacts the key. fetch_indicator is untouched.
- C9  signal_results stores contrib_a, contrib_b, contrib_c at run time, so a later rules.yaml edit
      cannot rewrite a stored week.
- C10 compound rules support "all conditions" only (a_labor_core). OR waits until a rule needs it.
- C11 Labels are bilingual in rules.yaml and in the API (ko and en). The page is English for now.

Schedule and failure handling
- The engine runs at backend startup when this ISO week (KST) has no snapshot, and then by an
  hourly check. It is due once per KST ISO week after Saturday 08:51 KST, when the US Friday close is
  in the data. A desktop app is not always on, so a machine woken on Sunday still gets the week's run.
- The hourly check does not run when MONEYVIEW_DISABLE_STARTUP_JOBS is set (the test suite sets it).
- Any FRED problem (no key set, network error, non-200, malformed body or dates) makes that series fall
  back to cached observations from fred_cache. A rule whose data is then too old becomes `stale`, with
  the reason in its note. POST /run still returns 200 with a `failures` list.
- A scheduled run that reported FRED errors is retried on each hourly check within the same ISO week
  after the cutoff, and logs a warning. A restart after a failed run does not retry: the snapshot
  exists, and POST /run repairs it.
- Failures are not persisted. GET /latest returns `failures: []` after a reload. Each stale result keeps
  its reason in `note`, which is persisted.
- The FRED key is read from FRED_API_KEY (loaded from config/.env). It is never shown on the page and
  never logged.

Primary data sources
- /api/v1/signals/run, /latest, /history, /rules and /manual/{rule_id}.
- FRED series (DGS10, CPILFESL, BAMLH0A0HYM2, DCOILBRENTEU, DFEDTARU, PAYEMS), through the FRED
  observations API, with the fred_cache table as fallback.- Spec: docs/superpowers/specs/2026-10-10-macro-signal-engine-spec.md
